# Изображение чашки в чекине

Клиентская часть и серверный контракт реализованы. Бэкенд находится в соседнем
репозитории `CoffeePeek-NET`. До выпуска клиента нужно развернуть MediaService,
применить миграцию Shops `20261012082218_CheckInDrinkPhoto` и обновить ShopsService.

## Поведение клиента

- Выделение работает в формах «В кофейне» и «Дома» для новых фотографий.
  Редактирование существующей записи сохраняет серверные фотографии и вырезку.
- Полные фотографии остаются в `photos` (до пяти).
- Из первого фото автоматически выделяются объекты переднего плана. Один объект
  выбирается автоматически; при нескольких пользователь выбирает чашку в превью.
- Для одного чекина сохраняется один прозрачный PNG `drinkPhoto` (до 768 пикселей
  по длинной стороне). PNG не проходит через JPEG-компрессию загрузчика фото.
- Удаление первого фото отменяет старую обработку, сбрасывает вырезку и запускает
  обработку нового первого фото. Заметка и остальные поля сохраняются.
- Пока идёт обработка, отправка недоступна. Можно отказаться от вырезки. Ошибка
  обработки сохраняет исходник и позволяет повторить попытку или отправить чекин
  без вырезки. Ошибка **загрузки** выбранной вырезки останавливает отправку чекина,
  чтобы незаметно не потерять выбранное изображение.
- Календарь и карточка напитка используют `drinkPhotoUrl` с `ContentScale.Fit`.
  Полноэкранная галерея продолжает использовать полные фото. Старые ответы без
  `drinkPhotoUrl` поддерживаются.
- В календаре вырезка имеет приоритет перед обычным фото. До трёх изображений
  складываются в стопку; остальные записи обозначены числом. Если вырезки нет,
  используется обычная миниатюра, а если нет фотографий — точки. Старые фотографии
  автоматически повторно не обрабатываются.
- Белая обводка повторяет силуэт PNG в календаре, предпросмотре и миниатюрах.
  Android-загрузчик сохраняет прозрачность при уменьшении изображения для экрана.
- Домашний календарь получает фотографии всех страниц истории выбранного месяца:
  endpoint `/home/calendar` возвращает только количество записей. Выбор дня и
  пагинация списка под календарём не заменяют изображения других дней.

Это выделение объектов, а не классификатор посуды: человек, рука или блюдце тоже
могут попасть в результат. Предпросмотр позволяет проверить его и отказаться от
неподходящей вырезки. Автоматическое распознавание именно класса «чашка» потребует
отдельной модели; оно не заявляется этой реализацией.

## API

### Загрузка

Используется существующий `POST /api/Photos/check-in`: сначала для полных фото,
затем отдельно для одного PNG. Формат запроса не меняется:

```json
[{"fileName":"drink_0.png","contentType":"image/png","sizeBytes":123456}]
```

Ответ — существующие `uploadUrl` и `storageKey`. Клиент выполняет PUT PNG без
перекодирования, с `Content-Type: image/png`.

### Создание

`POST /api/v1/check-ins` получает дополнительное необязательное поле `drinkPhoto`:

```json
{
  "coffeeShopSlug": "example-coffee",
  "visitedAt": "2026-10-12T09:00:00Z",
  "visibility": "Private",
  "photos": [
    {"fileName":"coffee.jpg","contentType":"image/jpeg","storageKey":"check-ins/full.jpg","size":456789}
  ],
  "drinkPhoto": {
    "fileName":"drink_0.png","contentType":"image/png","storageKey":"check-ins/cup.png","size":123456
  }
}
```

Остальные поля чекина сохраняют существующий смысл. `drinkPhoto` отсутствует или
равно `null`, если вырезка не выбрана. Оно связано с первым элементом `photos`;
его нельзя включать в список обычных фотографий и учитывать в лимите пяти фото.

Сервер проверяет принадлежность обеих загрузок пользователю, отсутствие повторного
использования, наличие полного фото при вырезке и содержимое PNG: до 4 МиБ,
1–768 px по каждой стороне, прозрачные и видимые пиксели. Анимация запрещена.
Проверяются байты неизменяемой приватной копии; перекодирования нет. Ошибка вырезки
отменяет создание всего чекина. Обе загрузки привязываются к одному чекину.
Неоднозначно завершившиеся привязки сохраняют резервирование для безопасного
повтора, как обычные фото; очистка таких резервирований не добавлялась.

### Чтение

Во всех представлениях чекина вернуть необязательное поле:

```json
{"drinkPhotoUrl":"/api/v1/check-ins/check-in-id/photos/cutout-photo-id"}
```

Клиент использует URL из ответа, а не конструирует его. Поле возвращается в
истории/календаре, обеих лентах, карточке кофейни, ответах создания,
редактирования и смены видимости.
URL может быть абсолютным или относительным к API. Для старых записей — `null`.

Доступ к PNG следует правилам полного фото чекина, включая приватность, актуальную
модерацию и удаление. В модерацию поступают обе версии. Ответ картинки сохраняет
прозрачность. Текстовое редактирование сохраняет вырезку: `UpdateCheckInReq`
намеренно не отправляет поля фотографий. Старым записям миграция оставляет `null`.

## Платформы и размещение кода

- Android: [ML Kit Subject Segmentation](https://developers.google.com/ml-kit/vision/subject-segmentation/android),
  Google Play services, модель загружается отдельно. На первом запуске может
  потребоваться интернет и повторная попытка. Без Google Play services
  автоматическое выделение недоступно; полный чекин можно отправить.
- iOS: [Vision foreground instance masks](https://developer.apple.com/documentation/vision/vngenerateforegroundinstancemaskrequest),
  начиная с iOS 17. На iOS 15–16 доступен чекин без вырезки. Минимальная версия
  приложения не менялась. Вызов Vision находится в Swift-провайдере с `#available`,
  чтобы Kotlin/Native не создал сильные ссылки на классы iOS 17 при запуске старых
  систем. Провайдер подключён к Xcode- и xtool-приложениям.
- Обработка снимка локальная; внешние сервисы удаления фона не вызываются.
- Новая обработка находится в `composeApp/.../feature/checkin`: контракт в
  `domain`, платформенные реализации в `data`, превью в `ui`. Корневая DI связывает
  реализацию с существующей формой чекина. DTO и загрузка расширены в существующих
  legacy-модулях, где пока находится транспорт чекинов. Новых Gradle-модулей нет.

## Проверка на устройствах перед выпуском

Проверка восстановления от 15.10.2026: прошли 179 unit-тестов приложения и 41
тест модулей data/home-checkin; `lintDirectDebug` завершился без ошибок;
`compileKotlinIosArm64` проверил Kotlin-код iOS. Swift-приложение и Vision требуют
отдельной проверки на macOS/iPhone.

На отдельном чистом эмуляторе Pixel 8 прошли 16 из 17 Android-проверок: календарь
показывает прозрачный PNG с белым контуром, выбор дат и формы работают; проверены
PNG-кодирование, предел 768 px, сохранение alpha при экранном уменьшении,
полупрозрачные пиксели и неизменность исходника. Проверка настоящего выделения
не дошла до обработки фото: Google Play `ModuleInstallClient` вернул
`state=5, error=8`, модуль сегментации не загрузился. Этот тест остаётся красным,
результат не заменён имитацией и не считается подтверждением работы модели.

Повторный запуск: `./gradlew :composeApp:connectedDirectDebugAndroidTest` при
подключённом устройстве/эмуляторе с Google Play services. При первой загрузке
модели тест явно запрашивает установку через `ModuleInstallClient`, ждёт до трёх
минут и выводит состояние/ошибку доставки. Затем выделение ограничено минутой.
Нужны интернет и работающая доставка модулей Google Play. Для UI-фикстур на чистом
устройстве разрешения геолокации выдаются до запуска Activity, чтобы системное
окно не перекрывало проверяемый экран.

Проверить чашку с ручкой, прозрачный стакан, чашку в руке, несколько чашек, фото
без чашки, повёрнутое фото, запуск без модели/сети, удаление фото во время обработки,
повтор после ошибки PUT и чтение приватного PNG после перезапуска приложения.
Особенно важны реальный iPhone с iOS 17+, iOS 15–16 и Android с первым запуском
модели: модульные тесты не оценивают качество нативной сегментации.
