# P4: check-in photo variants in KMP

Requires the additive backend contract from CoffeePeek/coffeepeek-backend PRs #346–#349.
The production slice was released through PR #105; PR #100 retains those photo fixes while integrating the other develop features.

Feed/shop/profile cards use feed previews, calendars use thumb, and a tap opens detail. A photo at least half visible for 1.5 seconds upgrades to its supplied detail URL. The loaded preview stays visible while detail loads or fails. Full-screen uses the ready detail representation immediately; a missing detail falls back to the current photo's original automatically. There is no original button. Original URLs and gallery order stay in the domain model. Home gallery and drink cutout descriptors are handled separately, preserving PNG alpha. JPEG/PNG is preferred for platform compatibility, with WebP as a supported fallback.

Protected immutable check-in variants use an application memory cache of encoded bytes (48 entries / 12 MiB, LRU). Its key includes the full source/recipe/purpose/format URL and an opaque rotating session scope. A response must explicitly permit private storage; `no-store` evicts bytes and ETag, while `max-age=0` may retain them only for online revalidation. After expiry, `If-None-Match` can restore the exact retained bytes only on an authorized 304 with a matching ETag and valid new policy. Denials, network failures, malformed metadata, missing candidates and unexpected 304 responses never show stale bytes.

Fresh reuse is capped by server `max-age`, 20 seconds and JWT expiry. RFC 9111 Date/Age accounting includes the entire request/body transfer time; wall and monotonic deadlines also account for residence and decoding. Missing/unreadable Date grants no positive reuse. A usable positive grant that expires before completion cannot display. An online no-store/zero-freshness response may authorize the current presentation until request start + 20 seconds, capped by JWT, without granting a later fresh hit. A new 304 uses its own Date/Age/policy; old observations cannot renew permission. Unknown/expired authenticated JWTs fail closed. Anonymous viewers may reuse an explicitly fresh private variant within the same opaque session scope and 20-second cap; sign-in or another local invalidation rotates that scope.

Display permission is separate from cached bytes. A bounded LRU retains decoded protected variant painters (48 entries / 24 MiB) only under an explicit reusable cache grant. Immediate repeat visits and prefetch reuse the same painter without another transfer or decode, within its original deadline. Online-only/no-store presentation grants never become reusable grants. The protected painter is removed at its actual permission deadline before reauthorization; it also clears on session/token changes, logout, local photo-affecting mutations and backgrounding. Resume checks both clocks before rendering. Kamel's unrestricted protected caches remain bypassed; ordinary bitmap caches on Android and iOS are bounded to 48 MiB. Original/private/home/moderation responses keep no-store behavior. The backend always applies bounded positive caching to eligible publicly visible variants; no cache feature flag or deployment setting is required.

Session installation accepts an optional local author-visibility flow. The application passes the author-blocking feature's visibility flow, while builds without that feature may use the default empty flow. Both forms observe credential/account/logout changes and revoke permission before and after photo-affecting HTTP mutations, including a lost mutation response. The optional flow does not change the server access checks or permission deadlines.

At most four image transfers run simultaneously. Duplicate variants share in-flight work within one session scope. Leaving the last subscriber cancels the transfer, including queued work; cancelled or invalidated responses cannot publish later or overwrite a replacement. Lists warm the next three items, with at most six distinct photo URLs and two speculative loads globally. A short debounce lets visible images claim slots first. Prefetch never renews unseen permission grants. A full-screen viewer pauses the covered screen's lookahead and delayed quality upgrades, warms adjacent detail previews, and renders both visible pages during a drag. Only a current photo without a ready detail may fall back to its original. Variant bodies stream with the backend's 8 MiB limit. Original iOS downloads still stream into the existing bounded decoder. The iOS decode mutex is retained until profiling. Android server variants skip decode/re-encode and go directly to the decoder; legacy originals retain EXIF handling.

Protected transfers use a dedicated authenticated Ktor client without `HttpCache`, plus request `no-cache, no-store` and explicit Darwin URL cache bypass. The request directive excludes lower transport caches; the separate application byte cache follows response policy. Ktor's HTTP cache otherwise intercepts manual 304 responses and can throw `InvalidCacheStateException`. API and image clients share refresh rotation coordination bound to the rejected request's actual bearer credential, including delayed 401 responses. An account switch never retries the old operation with another account. Other images retain their existing transport.

Unit coverage includes Date/Age/response delay, zero/no-store policy, missing Date, repeated/new 304 metadata, JWT expiry, clock changes, encoded/decoded LRU and byte limits, permission-scoped repeat hits, bounded lookahead, denied/offline loads, simultaneous subscribers, uncancellable old responses, evicted candidates, native cache exclusion and shared/delayed refresh rotation. Android fixture tests exercise dwell and clipped visibility, pending/failed quality upgrades, prefetch/reopen reuse, automatic pending-photo fallback, protected permission withdrawal, visible pages during a held drag, and cancellation across repeated dismissal. The fixtures run offline without an account or server mutations.

Remaining release gates: signed iOS/Android device runs, background/resume and rapid account switch, private/home access and both block directions against the real Gateway/Caddy, corrupt/EXIF/alpha cases, long-scroll memory, and download/decode/render measurements at 5 Mbit/s and 100 ms RTT. Windows KMP compilation does not prove an Xcode link or device behavior. Final concurrency tuning remains a measured change. No production flags are changed.
