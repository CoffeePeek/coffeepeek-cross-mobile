При ошибке GET остаётся карточка подтверждения с открытием записи и повторной загрузкой; повторного POST нет. Это временное подтверждение известного успешного сохранения, а не объединение feed с mine. Оно скрыто при фильтрах, очищается при успешной сверке, смене аккаунта, переводе в Private и удалении.
- Возврат из редактора и возобновление экрана обновляют ленту. Собственные Pending сохраняются после редактирования; Private/Rejected исчезают. Шаринг и лайки требуют одобрения; прежний лайк собственного одобренного поста сохранён.
- Только Rejected создаёт уведомление CheckIn. Event ID детерминирован по чекину, ревизии, submission и последовательности; повторная доставка не увеличивает inbox/unread. Старые queued approval push завершаются как Skipped, история уведомлений остаётся.
- Внутренний CheckInPost отличает ID чекина от старого submission ID. Inbox сохраняет совместимый entityType=CheckIn; новый клиент запрашивает destination?supportsCheckInPost=true, старый получает CheckIns.
- Новых Gradle-модулей нет. Root содержит адаптеры записей, DI и маршруты. Код общий для Android/iOS; Kotlin/Native на Windows не проверен.

## Согласованное поведение

- Применяется к публичным чекинам обоих типов: посещение кофейни и приготовление дома.
- После успешного сохранения автор видит чекин в своей общей ленте без статуса ожидания модерации.
- Остальные пользователи и гости получают чекин только после одобрения текущей версии.
- Одобрение происходит без push, записи в центре уведомлений, нового unread badge и сообщения об успехе.
- При отказе автор получает уведомление; чекин исчезает из общей ленты, включая ленту автора.
- Отклонённый чекин остаётся в личной истории с причиной и возможностью исправить.
- Выбор «Только мне» сохраняется: личные чекины не попадают в общую ленту даже автора.

Модерация остаётся серверным процессом. Клиент скрывает промежуточный статус в пользовательском интерфейсе, но не подменяет `Pending` на `Approved` в данных.

| Состояние | Общая лента автора | Лента других / гостя | Личная история | Уведомление автору |
| --- | --- | --- | --- | --- |
| Сохранён, Public + Pending | Обычная карточка | Нет | Есть, без статуса ожидания | Нет |
| Public + Approved текущей версии | Та же карточка | Есть | Есть | Нет |
| Public + Rejected | Нет | Нет | Есть, причина и исправление | Отказ |
| Private | Нет | Нет | Есть, «Только мне» | Нет |
| Удалён | Нет | Нет | Нет | Нет нового уведомления |

Неизвестный статус не считать одобрением. Ошибка сохранения не считается созданным чекином.

## Предлагаемая реализация

### 1. Персонализированная серверная выдача

Лента для авторизованного пользователя объединяет:

1. Записи, доступные ему по действующим правилам публичной выдачи.
2. Его собственные Public + Pending записи, соответствующие фильтрам ленты.

Проверять владельца по доверенной серверной идентичности сессии, не по `authorSlug` или переданному клиентом ID. Сохранить правила удаления, блокировок и скрытых кофеен. Отдельно проверить приоритеты условий в запросе: исключение для автора не должно отменять остальные ограничения.

Не менять общий `CheckInEligibility.Public`: иначе Pending начнут влиять на публичные рейтинги, счётчики и другие выборки. Добавить правило именно персонализированной ленты. Публичные профили, списки кофейни, веб-превью и поисковая индексация остаются публичными выборками; личная история служит автору полным списком его записей.

Состав и пагинацию формирует сервер. Клиент не склеивает отдельно загруженные `/feed` и `/mine`: это создаст неполную выборку, рассинхронизацию курсоров и различия между устройствами. Сохранить `no-store`, изоляцию по сессии, очистку состояния и отсечение запоздавших ответов при смене аккаунта.

### 2. Порядок и обновление ленты

Рекомендуемый вариант:

- Для автора позиция нового поста фиксируется при первой отправке в публичную ленту и не меняется из-за одобрения или редактирования.
- Для остальных сохраняется существующая сортировка по первой фактической публикации: одобренная запись появляется как новая, даже если проверка заняла время.
- Время посещения/приготовления остаётся отдельным пользовательским полем и не определяет эту позицию.
- `FirstPublishedAtUtc` сохраняет значение фактической публичной публикации; не заполнять его заранее ради Pending.

Для стабильной позиции автора потребуется отдельное поле времени первого включения в его ленту либо уже существующий эквивалент в актуальном backend. Если такого поля нет, добавить минимальную миграцию: для старых опубликованных записей использовать прежний `FirstPublishedAtUtc`; для старых Pending определить документированный fallback по доступной истории отправки. Не угадывать дату публикации по дате посещения.

В контракте нового режима различать время позиции в ленте и время публичной публикации. Курсор версионировать и связать с режимом, фильтрами и контекстом читателя; он не заменяет проверку доступа. Одобрение во время пагинации не должно дублировать собственную запись. Новые публичные записи выше курсора появляются при обновлении первой страницы. На клиенте сохраняется дедупликация по ID.

После создания/редактирования обновлять ленту через небольшой feature API и root wiring. Показывать серверно сохранённую запись сразу после успешного ответа; при необходимости дочитывать её по ID. Сбой обновления ленты не должен превращаться в повторный POST уже созданного чекина. Сохранять карточку и действия повторной загрузки в рамках текущей сессии, затем сверять с сервером. Для таймаута самого создания проверить существующий механизм идемпотентности до добавления нового.

### 3. Пользовательский интерфейс и редактирование

- После успешного создания: «Чекин добавлен». Не использовать утверждение «Уже доступен всем» до фактического публичного доступа.
- Убрать «На проверке», «Ожидает публикации» и объяснение обязательного ожидания из активных экранов создания, подтверждения, личной истории и деталей обоих типов.
- Pending и Approved у автора имеют одинаковое обычное представление карточки. Private сохраняет явный признак «Только мне».
- Rejected в истории получает понятную причину и действие «Исправить». При отсутствии причины — корректный общий текст, без пустого блока.
- Исправление отклонённого чекина создаёт новую ревизию того же чекина, отправляет её на проверку и возвращает карточку в ленту автора. ID не меняется; старый отказ не показывается как состояние новой версии.
- При редактировании одобренного поста сохранить текущую серверную политику: новая версия видна автору, остальные временно не видят пост до повторного одобрения. Хранение отдельной старой опубликованной версии не входит в этот срез.
- Переключение в Private и удаление сразу убирают карточку из общей ленты. Запоздалое решение модерации не возвращает её.
- Публичный шаринг остаётся доступен после одобрения. До него нельзя обещать работающую ссылку для другого пользователя. Прямой запрос чужого Pending/Rejected и его фото остаётся недоступным.

Изменения принадлежат `feature/community`, `shop`, `home-check-in`, `check-in-history`, `notifications` и при необходимости личному представлению `profile`. Root `composeApp` только связывает публичные контракты и маршруты. Новые Gradle-модули и общий core-модуль для модерации не нужны. Предпросмотры и строки обновляются в owning feature, на русском и белорусском.

### 4. Уведомления об отказе

- В Account на уровне создания пользовательского уведомления: для `CheckIn` принимать только применённое решение `Rejected`; для остальных типов модерации сохранить текущие правила.
- Одобрение не создаёт ни push, ни inbox-запись, ни unread count. Не скрывать уведомления только на клиенте: иначе push и счётчики останутся несогласованными.
- Внутренние события одобрения сохранить для публичной выдачи, инвалидации кэшей, аналитики и аудита.
- Отказ записывать в центр уведомлений, даже если push выключен. Push отправлять с учётом разрешения ОС и настроек пользователя.
- Текст: «Чекин не опубликован. Он сохранён в вашей истории. Откройте запись, чтобы посмотреть причину и исправить её». Подробную причину показывать внутри приложения.
- Переход должен открывать конкретный чекин в контексте владельца, включая домашний тип. Расширить destination-контракт совместимо; существующие уведомления без ID чекина могут по-прежнему вести в историю. ID заявки не трактовать как ID чекина.
- Событие отказа должно иметь устойчивую идентичность решения: чекин, ревизия, submission/sequence. Повторная доставка одного решения не создаёт второй отказ; отказ новой исправленной версии допустимо уведомляет заново.
- Сохранять атомарность применения решения и постановки события в существующий outbox. Старое решение не должно отклонять новую ревизию, Private или удалённую запись. При открытии старого уведомления показывать актуальное состояние чекина; уже прочитанный отказ остаётся историческим фактом.
- Перед переключением проверить очередь: ещё не доставленные уведомления об одобрении не должны уйти после включения нового правила. Уже доставленные push отозвать нельзя. Исторические inbox-записи по умолчанию не удалять массово.

### 5. Внедрение и совместимость

1. Перед кодом сверить актуальные backend/mobile/web ветки и реальные entry points. Этот документ не утверждает завершение legacy exit и не начинает реализацию в текущем analytics checkpoint. Реализацию вести отдельным согласованным срезом от актуального migration tip, соблюдая приоритет legacy exit.
2. Сначала реализовать backend-контракт, правила выдачи, стабильный порядок, адресацию отказа и тесты. Для совместимости использовать явный новый режим выдачи, например согласованный параметр `includeOwnPending`, либо версию API. Старые клиенты по умолчанию продолжают получать прежний публичный контракт. Параметр никогда не даёт доступ к чужим Pending.
3. Затем подключить новый режим в общем KMP-коде, обновить тексты, обновление ленты и переход из уведомления. Проверить реальные Android/iOS hosts; обновить активный веб-клиент либо явно сохранить для него старый режим.
4. После проверки включить новое поведение и отключение уведомлений об одобрении согласованно. Флаг нужен только на период совместимости и имеет условие удаления. Откат меняет режим выдачи; он не требует удаления чекинов или отмены модерации.

## Проверки и критерии приёмки

Для Shop и Home прогнать одинаковую матрицу автора A, другого пользователя B и гостя:

1. Успешное создание Public: A сразу видит запись и фото; после обновления/перезапуска она остаётся. B и гость не видят её в ленте, деталях, фото, публичном профиле и связанных публичных выборках.
2. Одобрение текущей ревизии: B получает запись; у A нет дубля, изменения позиции и нового уведомления. Публичные рейтинги меняются только по существующим правилам одобренных записей.
3. Отказ: запись исчезает из ленты A, остаётся в истории с причиной; создаётся ровно одно inbox-уведомление, push зависит от разрешений. Переход открывает нужный чекин, а не просто список.
4. Исправление: новая ревизия того же ID возвращается в ленту A; старая причина не выдаётся за актуальную. Старое/повторное решение не меняет новую ревизию и не дублирует уведомление.
5. Private, удаление, редактирование Approved, отказ после прежнего одобрения, скрытая кофейня и блокировка автора: проверены границы доступа и инвалидация ранее загруженных данных.
6. Смена аккаунта A → B/гость во время запроса, создания или открытия push: нет карточки, фото, кэша или перехода от предыдущей сессии.
7. Несколько страниц, фильтры по городу/кофейне/автору, смешанные Shop/Home и решение модерации между загрузками: правильная выборка, без дублей; смена фильтра/режима сбрасывает курсор.
8. Ошибки сети, повторное сохранение, запоздалые ответы и перезапуск: успешная запись не теряется и не создаётся повторно из-за ошибки обновления ленты.

Виды проверки при реализации:

- Backend: unit/contract и DB/HTTP integration-тесты eligibility, курсоров, revisions, outbox, уведомлений и защищённых фото; без production-записей.
- Mobile: domain/ViewModel/transport и non-UI composition-тесты затронутых feature; сохранить cancellation и session guards, existing analytics/consent contracts. Показ автору до одобрения не считать публичной публикацией в аналитике.
- Сборка Android с packaged DEX checks, `verifyFunctionBodyLimits`, `--max-workers=6`; Gradle-сборки последовательно. Проверка сборки iOS на доступном подходящем окружении.
- Ручная UI-проверка в явно выбранном `directSandbox`: оба типа чекинов, светлая/тёмная тема, большой шрифт, accessibility, модальные варианты, back/cancel, ошибки и уведомления. Обновить colocated previews; не создавать автоматические Compose/UI/screenshot тесты.
- Проверку реальной доставки push и backend-интеграции выделить отдельным этапом на согласованной безопасной конфигурации. Sandbox этого не подтверждает.

На этапе плана выполнен только анализ исходников. Сборки, тесты, запуск приложений и изменения данных не выполнялись.
