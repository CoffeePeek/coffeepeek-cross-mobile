# Реализация блокировки авторов

Backend: [draft PR #345](https://github.com/CoffeePeek/coffeepeek-backend/pull/345), коммиты `aa5588e8` и `83ab7a7f` (включение PostgreSQL-теста в CI).

Дата: 2026-10-18. План: [AUTHOR_BLOCKING_PLAN.md](AUTHOR_BLOCKING_PLAN.md).

## Реализовано

- Логическая фича `feature/authorblocking` в существующем `composeApp`: публичные межфичевые контракты в `api`, чистые модели/репозиторий в `domain`, Ktor/DTO и синхронизация в `data`, подтверждение и список в `ui`. Новых Gradle-модулей нет.
- Меню блокировки в общей ленте, чек-инах кофейни и чужого профиля, меню самого профиля. Жалоба остаётся отдельным действием. Собственные записи используют существующие edit/hide действия.
- Native destructive action sheet на iOS и лист подтверждения CoffeePeek на Android с отдельной группой отмены. Операция показывает немодальный статус с индикатором; ошибка предлагает повтор. Успех закрывает подтверждение без дополнительного alert. Для гостя — вход без автоматической блокировки после авторизации.
- Оформление использует токены CoffeePeek, шрифт Manrope, круглую кнопку назад, аватары и карточки проекта. Стандартные Material AlertDialog, ListItem и DropdownMenu в новых сценариях заменены презентационными компонентами дизайн-системы. iOS сохраняет системные UIMenu/UIAlertController; статус операции размещается над нативной навигацией без нового модального окна.
- Настройки → «Заблокированные авторы»: загрузка, пустой список, ошибка/повтор и подтверждение разблокировки.
- Серверное хранение, полный проход по страницам списка, стабильный opaque `authorId`, разрешение старых записей через slug, проверка результата после потерянного ответа. Локальное изменение видимости происходит только после подтверждения сервера.
- Общая ревизия видимости обновляет уже открытые ленты/профили/кофейни, сбрасывает курсоры и закрывает фото. Поздние страницы и ответы предыдущего аккаунта отбрасываются. Возврат приложения на передний план обновляет состояние и персонализированные выдачи. Личный дневник сохраняет своё поведение.
- Отдельная backend-реализация: Account migration/API, двусторонние ограничения, удаление взаимных подписок, запрет новых подписок/реакций, фильтрация до пагинации и проверка прямых detail/photo URL. SQL и HTTP остаются за серверными границами сервисов.

## Условия выпуска

Сначала развернуть backend с миграцией Account `20261018074440_AddPersonalAuthorBlocks`, затем клиент. Клиент ожидает `/api/v1/me/blocks`; при недоступном серверном состоянии не выдаёт пустой список за успешно загруженный и не подтверждает блокировку офлайн.

Блокировка A→B ограничивает взаимодействие и видимость в авторизованных сессиях обеих сторон. Независимая B→A сохраняется после разблокировки со стороны A. Подписки не восстанавливаются. Публичный контент остаётся доступным без авторизации; уведомление автору не отправляется. Жалобы и модерация продолжают работать отдельно.

## App Review Notes — маршрут проверки

Войти тестовым аккаунтом A → «Сообщество» → меню чужого чек-ина → «Заблокировать автора» → подтвердить. Публикации автора исчезают; профиль показывает состояние блокировки. Проверить то же через меню профиля. Открыть «Настройки» → «Заблокированные авторы» → «Разблокировать», подтвердить. Для жалобы использовать отдельный пункт «Пожаловаться» у чек-ина. Данные тестовых аккаунтов передать в App Store Connect отдельно, вне репозитория.

Основание: [App Review Guidelines 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content), [HIG Action sheets](https://developer.apple.com/design/human-interface-guidelines/action-sheets), [HIG Menus](https://developer.apple.com/design/human-interface-guidelines/menus). Наличие этой функции не заменяет модерацию и обработку жалоб.
