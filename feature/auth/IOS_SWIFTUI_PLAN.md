### Security Code Review Report — Debug 3224

Дата: 2026-11-25. Языки: Swift/SwiftUI/UIKit, Kotlin/Ktor/Keychain, Dart signing
tooling. Reviewer: secure-code-review v1.0.0. Проверка ограничена клиентской связкой
и локальным подписанным артефактом; серверные контроли не заверяются.

SCR-001 — неконкретная группа Keychain в development-подписи. Severity: Low;
CWE-732; ASVS V14.1.2. В фактическом Mach-O сборки 3222 первая группа была
`<prefix>.*`, хотя application-identifier уже содержал полный тестовый bundle ID.
`IosKeychainSessionStore` использует default group; ошибка SecItemAdd при сохранении
ответа авторизации проходит через AuthRepository в LoginFailure.Unknown.
Это подтверждённый дефект подписи; фактический статус SecItemAdd на телефоне и
результат конкретной попытки пользователя не были получены.
[Apple TN2415](https://developer.apple.com/library/archive/technotes/tn2415/)
требует конкретные группы в подписи приложения. Status: Mitigated в артефакте 3224;
проверка реального входа остаётся ручным gate.

Исправление: `tools/ios/sign_cached_debug.dart` подписывает bundle прежними
сертификатом/профилем и повторно подписывает только root executable с конкретной
default group. Нормализация не изменяет профиль, Team/App ID или предоставленные
права и не расширяет доступ; wildcard заменяется собственным application ID.
Используется Mach-O signer закреплённого xcross SDK, включая одинаковые XML/DER
entitlements и пересчёт подписи Info.plist/CodeResources. Проверка
`verify_signed_app.py` читает entitlements из результата и отклоняет старую 3222.
Никакого обхода Keychain, logout, очистки данных или записи токенов вне защищённого
хранилища нет. Rollback: нормальная Xcode-подпись либо другой проверенный подписанный
артефакт; ошибочная 3222 не является вариантом восстановления авторизации.

Apple Sign-In отсутствует в кешированном development-профиле тестового App ID.
Сборочный флаг `CoffeePeekAppleSignInEnabled` соответствует фактической подписи;
провайдер не регистрируется без capability. Обычный Xcode-путь без этого флага
сохраняет прежнюю настройку. Email/password контракт, HTTPS API URL и session guards
не менялись. Верхние back/close используют существующий Liquid Glass modifier.

### Form transition follow-up — Debug 3225

Полноэкранные iOS-формы больше не отправляют PopBack перед переходом на другую
форму. Один NavigateTo заменяет верхний Auth/Register в текущем UIKit-стеке одной
анимацией, сохраняя исходный экран под ним. Вход с другого экрана, восстановление
пароля и отдельный check-in auth flow сохраняют прежние маршруты. Новый чистый
root-navigation predicate проверяется JVM-контрактами; формы и credentials bindings
не пересоздаются для каждого изменения полей. Фактическое отсутствие мерцания при
переходах и клавиатуре остаётся проверкой на iPhone после полной сборки 3225.

Стартовый переход также сериализован: MainActor-owned UIKit dismissal adapter
завершает закрытие overFullScreen-лендинга и только в completion вызывает прежнее
действие Kotlin. Исходная модель остаётся активной до завершения анимации; её
существующие finished/isActive guards сохраняются. Повторное нажатие во время
закрытия игнорируется, контроллер удерживается слабо. Compose по-прежнему владеет
итоговым состоянием и маршрутом. Новых Swift Task, DispatchQueue, unchecked Sendable
или nonisolated-обходов нет. Правка Swift сделана до этапа Runner; подтверждено,
что закреплённый SDK передаёт исходные пути Swift непосредственно этому этапу.

Первый срез переводит маршруты `Auth` и `ForgotPassword` на SwiftUI. Оба iOS-лаунчера передают фабрику в существующий `NativeScreenController`. Kotlin-сессии создают ViewModel тех же классов, что и Compose-экраны, и закрывают их вместе с маршрутом. Закрытие контроллера отменяет наблюдения, OAuth-запрос и незавершённые действия ViewModel.

Пароль остаётся в памяти формы и Kotlin ViewModel. В модели состояния для SwiftUI он отсутствует. Парольные ошибки сохраняют правила Kotlin, а ошибки Apple и Google используют существующую классификацию и её диагностические коды. Доступность провайдеров определяется той же iOS-конфигурацией. Строки SwiftUI берутся из таблицы `NativeAuth` для текущего русского или белорусского языка CoffeePeek.

Отдельные `Register` и `ShopCheckInSignIn` подключены к той же SwiftUI-фабрике. В гостевом маршруте из ссылки чекина формы входа, регистрации и восстановления остаются внутри одного UIKit-контроллера. Введённые поля входа и регистрации сохраняются до выхода из маршрута. Восстановление получает адрес из формы входа; его кнопки возврата открывают ту же форму. `/reset-password` остаётся веб-маршрутом.

`Navigator` владеет запросом на продолжение чекина. Отмена в форме или уход гостя со страницы очищают запрос; при подтверждённой активной сессии сброс стека сохраняет запрос, и редактор открывается для исходной кофейни один раз. Успех парольной регистрации ожидает подтверждения почты и сам по себе не открывает редактор. Android использует общий механизм продолжения со своими Compose-формами.

Подготовка от `b8322a49f`. `ios-verify` запускает сборку iOS Simulator, контракты приложения и набор `:feature:auth:impl:iosSimulatorArm64Test`, включая отмену незавершённого входа и запроса на восстановление. Ручная проверка остаётся открытой для подходящего симулятора или устройства с тестовыми данными. Она охватывает клавиатуру и автозаполнение, отмену OAuth, навигацию из настроек и сценария чекина, ошибку с повтором, оба языка, темы, VoiceOver, увеличенный шрифт и переход по ссылке из письма.

Срез входа из чекина от `1c8dc7edb`: `ios-verify` отдельно исполняет `AppLinksTest`, `ShopCheckInSignInHandoffTest` и `IosCheckInAuthFlowTest`. Сценарии проверяют сохранение черновиков, предзаполнение восстановления, отмену ожидающего запроса и однократное продолжение в исходной кофейне после активации сессии. Ручное прохождение ссылки, системного жеста назад и реального Apple/Google-входа не выполнялось.
